# ADR: Один входящий вебхук Bitrix24 на интеграцию (REST-префикс для n8n)

## Статус

Принято (пояснение границы B24 ↔ n8n).

## Контекст

В обсуждениях смешиваются:

1. **Именованные webhooks в n8n** — отдельные URL/path под каждый сценарий (`registration/crm-company-get-v1`, …); задаются ключами `registration_webhook_*` на сайте (см. ADR «один метод — один n8n webhook»).
2. **Входящий вебхук в Bitrix24** — объект в разделе разработчика портала, дающий **один** базовый URL вида `https://<portal>/rest/<user>/<secret>/`, к которому добавляются имена методов (`crm.contact.add.json` и т.д.).

Вопрос «сколько входящих вебхуков создать в B24» относится только к пункту (2).

## Решение

- По умолчанию создаётся **один** входящий вебхук Bitrix24 на интеграцию «n8n → портал».
- Строка **`EKLEKTIKA_B24_REST_PREFIX`** в окружении n8n задаёт этот базовый префикс (без завершающего слэша или с нормализацией в workflow).
- Множественные пути на стороне n8n **не** требуют множества входящих вебхуков в B24: вызывается один и тот же REST-префикс, меняется только тело запроса (`METHOD`/`PARAMS` или форма для конкретного `crm.*`).

## Когда нужно больше одного входящего вебхука B24

- Разные **наборы прав** (отдельный пользователь интеграции с ограниченным CRM-доступом vs полный).
- Разные **порталы или стенды** (prod/stage) — отдельный вебхук на окружение.
- Политики **ротации секретов** (перевод на новый вебхук с overlap).

## Последствия

- Документация по ключам `registration_webhook_*` описывает **n8n**, а не создание десятков объектов «входящий вебхук» в B24.
- Проверка прав: пользователь (или приложение), привязанное к **единственному** входящему вебхуку, должен иметь доступ ко всем `crm.*`, которые реально вызываются из регистрации (см. `CrmRegistrationOrchestrator::registrationCrmRestWebhookConfigKey()` и отдельные webhooks inn/company/contact/async).
